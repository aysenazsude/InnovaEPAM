# Implementation Plan: Draft Management — Phase 4

**Branch**: `004-draft-management` | **Date**: 2026-05-14 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/004-draft-management/spec.md`

## Summary

Phase 4 adds server-side draft persistence to the idea submission flow. Submitters can save a partially-completed idea form (including category-specific fields and attachments from Phases 2–3) as a named draft, resume editing it across sessions and devices, and either submit it as a final idea or delete it. The implementation adds three new SQLite tables (`drafts`, `draft_category_data`, `draft_attachments`), five new server actions, a drafts list page, and extends the existing `IdeaForm` component with `draftId` / `defaultValues` props — with no changes to the existing `ideas` or `attachments` tables.

## Design Decisions

### DD-01: `draftRepository.ts` extraction

To keep `src/lib/actions/drafts.ts` under 300 lines (Principle I), database query logic for drafts is extracted into `src/lib/drafts/draftRepository.ts`. This file exposes typed query functions (`findDraftsByUser`, `findDraftWithAttachments`, `countDraftsByUser`, `insertDraft`, `updateDraft`, `deleteDraftById`) used exclusively by `drafts.ts` actions. This is not a Repository pattern abstraction — it is a file-length decomposition of a single concern.

### DD-02: `IdeaForm` draft mode activation

`IdeaForm` receives `draftId?: string` and `defaultValues?: DraftFormValues`. When `draftId` is defined:
1. The form title changes to "Edit Draft"
2. A "Save Draft" button appears (secondary style) alongside "Submit"
3. A hidden `<input name="draftId">` carries the ID through the form action
4. A hidden `<input name="version">` carries the concurrency token

No internal booleans or flags — all behaviour is driven by the presence/absence of `draftId`. This ensures the default (new idea) path is zero-cost.

### DD-03: Attachment reconciliation on re-save

When a draft is re-saved with a modified attachment list:
- Attachments in `draft_attachments` but NOT in `existingAttachmentIds` from FormData → `deleteFile` + DELETE row
- New `File` entries in FormData → validate, `saveFile`, INSERT row
- Attachments present in both `existingAttachmentIds` and `draft_attachments` → untouched

This is the same reconciliation pattern used in the Phase 3 attachment re-upload flow, keeping the logic consistent.

### DD-04: No dedicated draft attachment upload API route

Draft attachment files are saved on the server during `saveDraft` (server action), not via a separate upload endpoint. This keeps the flow synchronous and consistent with `submitIdea`'s current approach. A future enhancement could add incremental async upload for large files, but this is out of scope for Phase 4.
